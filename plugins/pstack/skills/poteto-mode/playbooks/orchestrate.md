### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it with your own native Antigravity tools. Spawn workers with `swarm` (`action: "add"`, `model: "<slug>"`, `workspace: "share" | "branch"`) or `invoke_subagent` (`TypeName: "poteto-agent"`, `Workspace: "share" | "branch"`). Keep the program's state in `<appDataDir>/brain/<conversation-id>/notes.md` (and `decisions.tsv` via the **show-me-your-work** skill). Watch PRs with `scripts/watch-pr/watch-pr` and `schedule` heartbeats. Call no bespoke orchestration scripts, run no busy-polling loops, and never relay raw status chatter between agents.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers do not assume visibility into sibling context. Run workers in isolated workspaces (`workspace: "share"` or `"branch"` in `swarm`, or `Workspace: "share"` or `"branch"` in `invoke_subagent`) unless the work needs the parent workspace directly: live UI or CLI verification (`.agents/skills/verify-<app>/`, `TypeName: "browser"`, `cua-driver`, `run_command`), reading local transcripts under `<appDataDir>/brain/<conversation-id>/.system_generated/logs/`, a simulator, or auth that exists only in the parent checkout. Pick each worker's model and reasoning level for the job, per the Subagents section (never `gpt-oss-*`).
- **A sub-coordinator only when one area has many parallel workers.** Spawn it with `invoke_subagent` (`TypeName: "poteto-agent"`) or `swarm`. It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep about ten workers in flight per coordinator, and start the next one as each finishes instead of waiting on a whole batch.
- **Fork when new work needs a worker's built state,** such as its checkout, uncommitted changes, or a running process (`fork: "<member>"` in `swarm`, or `send_message` to an existing `invoke_subagent` conversation). Message a worker only for a follow-up on the same work. Never message one to check on it, because a message wakes an idle agent. Use `swarm(action: "status")` or `manage_subagents(Action: "list")` for read-only inspection, and call `swarm(action: "kill", name: ...)` only after a worker's branch/output is pushed or landed.
- **Each PR gets a verifier that isn't its author,** on a different model family (`claude-*` vs `gemini-*`, checking `swarm(action: "models", all: true)` for live quota first). The owner merges only on that verifier's pass at the current head.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a verification-skill check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model (or `swarm(action: "model", ...)` switch) after a tool or quota error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.
